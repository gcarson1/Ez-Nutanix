| 12 | Bond modes and Prism names; behavior on link failure; rebalancing interval. | **Prism "Bond Type" names are confirmed:** **Active-Backup** = active-backup (default, recommended); **Active-Active with MAC pinning** = balance-slb; **Active-Active** = balance-tcp with LACP; **No Uplink Bond** = 0 or 1 uplink. Every type except No Uplink Bond needs at least 2 uplinks per node. Don't mix bond modes across hosts. **Active-Backup:** one NIC is chosen at random as active when the host boots, and the others carry nothing until it fails, then a backup takes over. VM and host are limited to one link (10G on 2×10G). No switch config is needed and it works across two switches. Since BP v4.9 the active uplink can be pinned per host with `acli net.update_virtual_switch ... active_uplink=...`. **MAC pinning (balance-slb):** each VM NIC (source-MAC hash) uses one adapter at a time. On link failure, OVS moves the failed link's hashes to the surviving link. Don't use it with LACP. ## Corrections to the brief

1. **Pre-checks come before ordering.** The LCM engine order is: framework self-update -> **pre-checks** -> batch/order by dependency -> one node at a time (pre-update -> update -> post-update) -> next node once **Data Resiliency is Normal**. The user does see dependencies first, because they are auto-selected while choosing updates (HBA pulls in Disks). The UI names the plan step "View Upgrade Plan" in PE and "Create Upgrade Plan" in PC, and the commit button "Apply Updates" (PE) or "Apply Upgrade Plan" (PC).
2. **Current LCM is 3.4** (not "3.x" generically). The current platform is AOS 7.6, AHV 11.2 and pc.7.6 (July 2026). Since 7.5, AHV is a separate LCM update from AOS. AOS 6.8+ can only be upgraded through LCM, and 1-click AOS upgrade is deprecated as of LCM 3.0.
3. **On AHV, AOS-upgrade I/O redirection is the iSCSI redirector, not "autopathing".** "CVM Autopathing" (HA.py rerouting 192.168.5.2) is the ESXi/Hyper-V term. For hypervisor and firmware updates, VMs are evacuated first, so there is no local guest I/O to redirect.
4. **Pre-check names:** test_cluster_status, test_under_replication, test_zk_status, test_check_revoke_shutdown_token and test_upgrade_in_progress are **LCM 2.x-documented names**, now handled as module pre-checks. "Free space on CVM" is actually **test_nutanix_partition_space** (/home/nutanix). URL connectivity is **test_check_url_connectivity**. Names actually in the 3.x framework list that are worth showing: test_ncc_checks, test_hosts_in_maintenance_mode, test_ahv_entering_mm_pinned_vms, test_lacp_configuration and test_node_removal_status.
5. **Firmware maintenance environment:** in LCM 3.4 the NX Redfish flow calls it the **Phoenix environment module (PEM)**. Reboot counts are BMC 2 and BIOS/CPLD/LCMC 3, so "possibly multiple reboots" should be "always 2–3".
6. **Single-node:** LCM **does not do firmware** on 1-node clusters. AOS and AHV upgrades are supported but **all guest VMs must be shut down manually first**.
7. **Two-node:** a **Witness VM must be registered** for any LCM or maintenance workflow. The cluster stays up but the upgrade takes longer (it has to resync data between the single-node and two-node states). Virtual-switch changes on 1- or 2-node clusters require powering off user VMs.
8. **Vendor list:** LCM 3.4's firmware platforms are NX, Dell XC/XC Core, Lenovo HX/HX Ready, HPE DX, HPE DL (G10), Fujitsu XF, Intel DCB and Cisco UCS M6/M7/M8. **Drop Inspur**, which appears only in the older FAQ.
9. **NKE (Karbon) is incompatible with pc.7.5+.** Show NKP instead, or omit it. The PC-side LCM entities are PC, MSP, Objects, Files Manager, Foundation Central, Self-Service, Network Controller, FNS PC and Security Dashboard CVE data.
10. **balance-slb is no longer "recommended for no-LACP".** BP-2071 (2026) says Nutanix doesn't recommend it because of multicast/IGMP-snooping problems. Active-Backup remains the default and recommendation, and LACP balance-tcp is the throughput option.
11. **"LACP fallback" is not a bond mode.** It is a setting of Active-Active (LACP), which Prism always enables (fallback to active-backup) together with LACP fast (1 s).
12. **Rebalance interval:** use the OVS default of **10 s**. Do not present 30 s as current official guidance.
13. **manage_ovs is not formally deprecated.** It is legacy for changes: use the Prism Virtual Switch (aCLI `net.*_virtual_switch`), which also reverts manage_ovs edits. Host VLAN tagging on AHV 10+ uses **nmcli**, not `ovs-vsctl set port br0 tag=`.
14. **Mid-upgrade second failure:** don't animate "no impact". On RF2 a second node down exceeds FT1, so data may be unavailable until a node returns. LCM itself halts and waits for the fix, and there is no automatic rollback.

### Corrected sequences to encode

**A. LCM update (one cluster, PE):**
1. Perform Inventory, which also updates the framework.
2. Updates > Software / Firmware: select the updates (dependencies are auto-added).
3. Run the NCC check.
4. Run the pre-upgrade checks.
5. View Upgrade Plan.
6. Review VM migration and non-migratable VMs.
7. Apply Updates.
8. LCM batches the updates by dependency.
9. For each node, one at a time: pre-update actions -> update -> post-update actions -> wait for Data Resiliency to be Normal -> next node.
10. Done.

**B. Per node (AHV upgrade or firmware):**
1. Host enters maintenance mode: live-migrate HA VMs; power off pinned, RF1 and agent VMs.
2. CVM enters maintenance mode.
3. CVM shuts down, holding the shutdown token.
4. Apply the update:
   - AHV in-place: upgrade packages, then reboot the host.
   - Firmware: reboot into Phoenix/PEM, flash, reboot back to the hypervisor (2–3 reboots).
5. CVM powers on.
6. CVM exits maintenance mode.
7. Host exits maintenance mode.
8. VMs migrate back and non-migratable VMs restart.
9. Shutdown token is released.
10. Wait for Data Resiliency OK.
11. Next node.

**C. Per CVM (AOS upgrade):**
1. Pre-checks.
2. Upload binaries to 2 CVMs.
3. All CVMs stage to the passive partition in parallel.
4. One CVM at a time:
   - The CVM takes the token.
   - The host stays up and its VMs stay on it.
   - The iSCSI redirector sends that host's VM I/O to remote Stargates.
   - The CVM reboots into the new partition.
   - Services come up and local I/O fails back.
   - The token passes to the next CVM.

**D. Virtual switch change (Standard method):**
1. Node into maintenance mode.
2. Apply the uplink or bond settings.
3. Check the default gateway.
4. Node out of maintenance mode.
5. Next node.

The Quick method skips maintenance mode and is for non-production only.

## Could not verify

- **The exact current LCM patch (3.4.x).** The LCM release notes weren't readable. One community post (Sept 2026) mentions a 3.4.0.1 remote framework version, which is unconfirmed.
- **The official "different node fails mid-update" behavior.** This is inferred from the documented "waits until you resolve the problem", "next node when resiliency Normal" and RF2 single-node-down rules. No doc describes that exact scenario.
- **Shutdown token internals** (ZooKeeper entry, Genesis-master grant, 30 s retry, release after HA routes are removed). These come only from Nutanix-employee community posts from 2020–2021, not from current portal docs. Whether test_check_revoke_shutdown_token still runs as an LCM 3.x module pre-check is unconfirmed. KB-7071 exists, but the check is absent from the 3.x framework table.
- **Current Nutanix-recommended balance-slb rebalance interval.** BP-2071 v4.9 no longer states one, and the 10 s figure is the OVS default.
- **aCLI enum for balance-slb.** `kBalanceSlb` is presumed but doesn't appear in the AOS 7.6 aCLI examples, which show only kActiveBackup, kBalanceTcp and kNoBond.
- **Non-NX firmware mechanics** (Dell iDRAC/iSM, HPE iLO/SPP, Lenovo XCC, Cisco UCSM/Intersight): whether each boots into Phoenix, and how many reboots it takes. The LCM 3.4 PEM reboot counts apply to NX only.
- **NKP lifecycle through LCM.** The LCM product page lists NKP, but the LCM 3.4 PC entity table doesn't.
- **Per-node durations.** The only figures are 2021 Nutanix-employee and community estimates, with no current official numbers.
- **Doc contradiction:** the LCM 3.4 "General Hypervisor Upgrade Recommendations" still says hypervisor upgrades can't be done from Prism Central. The same guide documents upgrading PE clusters from PC's "Prism Element Clusters" tab (minimum AOS 7.0.1.6 + pc.7.3). The safe on-screen wording is "LCM in Prism Element (or Prism Central for registered clusters on AOS 7.0.1.6+/pc.7.3+)".
- **CVM eth1 holding both 192.168.5.2 and 192.168.5.254.** The portal confirms .254 (CVM) and .1 (host). The .2 role and the eth1 label come from the Nutanix Bible, a Nutanix-employee community answer, and third-party sources.
